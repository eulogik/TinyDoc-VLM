# Invoice transfer probe (synthetic)

This harness measures the TinyDoc prompt/schema on invoices. It is **not** a
real-supplier invoice benchmark and not an independent evaluation.

## Corpus

[Invoice Extraction Benchmark v1](https://github.com/DrewKraken/invoice-extraction-benchmark)
(`drew-ipp/invoice-extraction-benchmark`, CC BY 4.0): 181 synthetic invoices
generated by InvoiceParser Pro from seed 42, with answer keys and a scorer.
Categories: clean 31, currency 19, tax 14, credit 10, multipage 10, freight 16,
scan 15, photo 45, handwritten 8, hard 13.

Caveats that must travel with every number:

- **Synthetic and vendor-made.** One layout engine, simulated damage, mostly
  English. It says nothing about a particular company's real invoices.
- **Page 1 only.** PDFs are rendered at longest edge 1800 px; multi-page totals
  may be missed. This is a first-page probe.
- **Not tuned.** The prompt and normalization were written before the run and
  were not adjusted against the answer keys.
- **Line items and flags are secondary.** The plan's invoice gate is the key
  header field rate; line-item F1 and flag behavior are reported separately.

## Current result (2026-11-06, re-normalized 2026-11-07)

Qwen2.5-VL-3B, 181/181 parsed, no errors:

| Metric | 3B | 2B |
|---|---:|---:|
| Key header field accuracy | 91.9% (1448/1576) | **93.5%** (1474/1576) |
| Documents fully correct | 65.7% (119/181) | **71.8%** (130/181) |
| Line-item F1, mean | 0.929 | 0.904 |
| p50 / mean latency | 26.5 s / 28.7 s | **16.1 s / 20.3 s** |
| Inconsistent invoices flagged | 0/5 | 0/5 |
| Multi-invoice files flagged | 0/2 | 0/2 |
| Consistent docs falsely flagged | 2/172 | 0/172 |

The 2B is at least as good on invoices and 40% faster; the paired per-document
sign test is not significant (p=0.092), so this is “no evidence that 3B is
better on invoices”, not a proof that 2B is. Do not generalize to receipts: the
3B still leads clean-100 there (0.9475 vs 0.9200). See
`results/compare_invoice_3b_vs_2b.json`.

This clears the 0.80 field-accuracy bar on synthetic page-1 data, but **not**
straight-through processing: 28–34% of documents still have at least one
key-field miss, flagging is unusable, and multipage is 0% fully correct. Real
supplier invoices are still unmeasured.

The first pass scored valid currency symbols (`N$`, `R`, `€`) as non-ISO and
understated accuracy (90.6% / 55.8%). Raw model outputs are unchanged; the
normalizer now maps symbols to ISO codes and the superseded pass is archived as
`results/*_v1_currency_symbols.*`. Artifacts: `results/`.

## Multipage path (wired, not yet measured)

The published probe above is page 1 only. A real multipage path is now wired so
the 10 `multipage` documents (46 pages total) can be measured as full documents:

```bash
python3 evaluation/invoice/build_manifest.py \
  --corpus "/Volumes/KIOXIA 1TB/tinydoc/invoice_benchmark_v1/corpus/v1" \
  --render-dir "/Volumes/KIOXIA 1TB/tinydoc/invoice_benchmark_v1/rendered_mp1400" \
  --out evaluation/invoice/manifest_multipage.jsonl \
  --ids multipage-2p-za-1 multipage-2p-us-2 multipage-3p-na-3 multipage-3p-gb-4 \
        multipage-4p-za-5 multipage-5p-de-6 multipage-5p-na-7 multipage-6p-za-8 \
        multipage-8p-us-9 multipage-8p-na-10 \
  --all-pages --max-dim 1400
```

This renders all 46 pages at longest edge 1400 px and emits `image_paths` per
document. `run_invoice_eval.py` sends every page image in one request and uses
`multipage_prompt()`, which asks for document-wide totals and tells the model to
read every page. Use `TINYDOC_OLLAMA_NUM_CTX=16384` for 5–8 page files.

**No multipage inference result exists yet.** Running it needs explicit approval
under `AGENTS.md`. Do not claim multipage accuracy until rows, scores, and the
claim audit exist. The 0% fully-correct result for multipage documents in the
table above is an artifact of page-1-only rendering, not a measurement of the
multipage path.

## Files

- `build_manifest.py` — render page 1 of PDFs with pypdfium2 (or every page with
  `--all-pages`), emit JSONL with the benchmark's expected values and
  `image_paths`. Requires pypdfium2.
- `manifest_v1.jsonl` — local page-1 manifest (absolute image paths; not
  committed because the corpus lives on the external disk). Rebuild with the
  command below.
- `manifest_multipage.jsonl` — local all-pages manifest for the 10 multipage
  documents (46 pages, ≤1400 px; not committed for the same reason).
- `run_invoice_eval.py` — Ollama runner; writes per-document rows and a
  benchmark-format `predictions.json`.
- `../../scripts/run_invoice_probe.sh` — runner + memory guard + scorer.

## Reproduce

```bash

git clone --depth 1 https://github.com/DrewKraken/invoice-extraction-benchmark \
  "/Volumes/KIOXIA 1TB/tinydoc/invoice-extraction-benchmark"

  "/Volumes/KIOXIA 1TB/tinydoc/invoice_benchmark_v1"

# 2. Render page 1 and build the manifest (needs pypdfium2; a venv is cleanest)
#    python3 -m venv .venv && .venv/bin/pip install pypdfium2 pillow
python3 evaluation/invoice/build_manifest.py \
  --corpus "/Volumes/KIOXIA 1TB/tinydoc/invoice_benchmark_v1/corpus/v1" \
  --render-dir "/Volumes/KIOXIA 1TB/tinydoc/invoice_benchmark_v1/rendered" \
  --out evaluation/invoice/manifest_v1.jsonl

# 3. Run one model (multi-document inference; get approval first)

scripts/run_invoice_probe.sh qwen3-vl:2b-instruct qwen3-vl_2b_instruct

# 4. Or score an existing predictions file directly
cd "/Volumes/KIOXIA 1TB/tinydoc/invoice-extraction-benchmark"
python3 -m scorer.evaluate <predictions.json> --out scores.json \
  --markdown scores.md --allow-missing
```

## Normalization choices

The runner maps the model output into the benchmark schema and resolves date
ambiguity before scoring. The benchmark scorer parses dates day-first, which
would silently flip `03/12/2024` on a US invoice; the runner uses the document
id/currency (`-us-` or USD → month-first, otherwise day-first). Amounts accept
dot decimals, comma decimals, thousands separators, and parenthesized negatives.
Unparseable dates are passed through unchanged and scored as wrong.

`document_type` maps `credit`/`credit note` to `credit_note` and
`statement`/`other` to `other`; everything else defaults to `invoice`.

## Reporting rules

- Name it **“synthetic invoice transfer probe (Invoice Extraction Benchmark v1)”**.
- Never cite it as real-invoice accuracy or an external/independent benchmark.
- Always say **page 1 only**.
- Report key header field accuracy and fully-correct rate; line-item F1 and
  flags separately.
- Keep the per-category breakdown visible: clean digital PDFs and phone photos
  are different products.
