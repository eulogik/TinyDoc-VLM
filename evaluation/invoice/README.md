# Invoice transfer probe (synthetic)

This harness measures the TinyDoc prompt/schema on invoices. It is **not** a
real-supplier invoice benchmark and not an independent evaluation.

> **Real-document probe:** `PT_REAL.md` documents the separate 100-document
> Portuguese invoice/receipt probe built from public CC BY 4.0 phone photos;
> `PT_REAL_RESULTS.md` reports the first measurement. It is a five-field
> transfer probe, not a nine-field invoice benchmark and not a leaderboard
> result.

## Corpus

[Invoice Extraction Benchmark v1](https://github.com/DrewKraken/invoice-extraction-benchmark)
(`drew-ipp/invoice-extraction-benchmark`, CC BY 4.0): 181 synthetic invoices
generated by InvoiceParser Pro from seed 42, with answer keys and a scorer.
Categories: clean 31, currency 19, tax 14, credit 10, multipage 10, freight 16,
scan 15, photo 45, handwritten 8, hard 13.

Caveats that must travel with every number:

- **Synthetic and vendor-made.** One layout engine, simulated damage, mostly
  English. It says nothing about a particular company's real invoices.
- **Page 1 only.** PDFs are rendered at longest edge 1800 px; multi-page totals
  may be missed. This is a first-page probe.
- **Output budget.** The page-1 runs used `num_predict=768`. One non-multipage
  row (2B) hit the cap but was fully correct on every key field; the multipage
  page-1 rows were cut off, and they score 0% fully correct regardless.
- **Not tuned.** The prompt and normalization were written before the run and
  were not adjusted against the answer keys.
- **Line items and flags are secondary.** The plan's invoice gate is the key
  header field rate; line-item F1 and flag behavior are reported separately.

The published probe above is page 1 only. A real multipage path is now wired so
the 10 `multipage` documents (46 pages total) can be measured as full documents:

```bash
python3 evaluation/invoice/build_manifest.py \

  --render-dir "/Volumes/KIOXIA 1TB/tinydoc/invoice_benchmark_v1/rendered_mp1400" \
  --out evaluation/invoice/manifest_multipage.jsonl \
  --ids multipage-2p-za-1 multipage-2p-us-2 multipage-3p-na-3 multipage-3p-gb-4 \
        multipage-4p-za-5 multipage-5p-de-6 multipage-5p-na-7 multipage-6p-za-8 \
        multipage-8p-us-9 multipage-8p-na-10 \
  --all-pages --max-dim 1400
```

This renders all 46 pages at longest edge **1400 px** and emits `image_paths` per
document. The page-1 probe uses **1800 px**, so multipage line-item F1 is **not
directly comparable** to the page-1 line-item F1: small table text is harder to
read at 1400 px. Key header fields are large and much less resolution-sensitive.

`run_invoice_eval.py` sends every page image in one request and uses
`multipage_prompt()`, which asks for document-wide totals and tells the model to
read every page. Run it with a larger output budget and context:

```bash
INVOICE_MANIFEST=evaluation/invoice/manifest_multipage.jsonl \
INVOICE_ALLOW_MISSING=1 INVOICE_NUM_PREDICT=5120 \
TINYDOC_OLLAMA_NUM_CTX=16384 TINYDOC_OLLAMA_TIMEOUT=600 \
scripts/run_invoice_probe.sh qwen3-vl:2b-instruct qwen3-vl_2b_mp
```

The 6- and 8-page invoices have **98–117 line items**; the page-1 default
`num_predict=768` cuts them off mid-JSON. A first pass with 768 is archived as
`results/archive/*_num768_truncated.jsonl` — it is not a result and must not be
cited. The rerun records `prompt_eval_count`, `eval_count`, and `done_reason` per
row so a context or output cut is visible instead of silent.

### Page-by-page variant (measured 2026-11-09; reconciled 2026-11-10)

`run_invoice_pagewise.py` sends **one page per request**, asks for that page's
line items and header fields, drops carried/brought-forward and total rows in
code, then merges: first non-empty header, concatenated line items, and
final-page totals. Printed totals and printed tax are authoritative: a small
subtotal residual is resolved toward `total - tax`, a nonzero tax below 0.1% of
the total is derived from `total - subtotal` (a leading-digit truncation), and a
total is derived from `subtotal + tax` only when it is missing or structurally
impossible. Inconsistencies are flagged rather than silently rewritten. No
repair reads gold. The canonical prompt is **v1**.
Run it with approval:

```bash
python3 evaluation/invoice/run_invoice_pagewise.py \
  --manifest evaluation/invoice/manifest_multipage.jsonl \
  --model qwen3-vl:2b-instruct \
  --prompt-version 1 \
  --out evaluation/invoice/results/rows_invoice_qwen3-vl_2b_mp_pagewise.jsonl \
  --preds evaluation/invoice/results/preds_invoice_qwen3-vl_2b_mp_pagewise.json \
  --resume
```

Prompt v2 added an explicit printed-symbol map (`N$` = NAD, `R` = ZAR,
`$` = USD, `€` = EUR, `£` = GBP, `K` = ZMW) and a `currency_symbol` field. It
**did not help**: the raw v2 run scored 81/90 key-header and 5/10 fully correct
versus 84/90 and 6/10 for v1, and one final-page total regressed to 390.50. The
deterministic last-page currency rule plus OCR totals fixed the same documents.
Keep v1; v2 is archived as a failed variant, not a claim.

| Metric | All pages, VLM | Page-wise, VLM | + merge reconciliation | + OCR totals |
|---|---:|---:|---:|---:|
| Key-header accuracy | 71.1% (64/90) | 93.3% (84/90) | 95.6% (86/90) | **100% (90/90)** |
| Documents fully correct | 4/10 | 6/10 | 8/10 | **10/10** |
| Mean line-item F1 | 0.322 | 0.848 | 0.848 | **0.848** |
| Parse errors | 2 | 0 | 0 | **0** |
| p50 latency per document | 34.7 s | 70.7 s | 70.7 s | 70.7 s |
| p50 latency per page | 8.9 s | 16.1 s | 16.1 s | 16.1 s |

All 46 pages parse; the 8-page files have 117/117 and 110/110 line items. The
10/10 is the benchmark's **nine key-header fields**, not line items. The exact
95% CI for 10/10 fully correct is **69.2-100%** (n=10), so this is a descriptive
probe, not proof of production accuracy. Line items remain weak: F1 0.848, all
lines right on **1/10**, and 8/10 trigger a line-sum-vs-subtotal review flag.
OCR plus rebuild adds 2.1 s for all 10 documents (~0.2 s/doc), so latency is
dominated by page-wise VLM inference.

Three documents have recorded corrections (no gold): `multipage-2p-za-1`
(subtotal/tax/total from OCR), `multipage-3p-na-3` (subtotal residual plus
currency from OCR), and `multipage-6p-za-8` (truncated tax). Paired changes:
page-wise VLM -> OCR, key improved 4 / regressed 0 (p=0.125), fully correct
gained 4 / lost 0 (p=0.125); all-pages -> OCR, key improved 6 / regressed 0
(p=0.03125), fully correct 6 gained / 0 lost (p=0.03125). n=10, synthetic, clean
PDFs; neither result transfers to real invoices. Artifacts:
`results/summary_invoice_qwen3-vl_2b_mp_pagewise_ocr.json`,
`results/compare_invoice_pagewise_vs_ocr_2b.json`,
`results/compare_invoice_mp_allpages_vs_ocr_2b.json`,
`results/audit_invoice_qwen3-vl_2b_mp_pagewise_ocr.json`.

`rebuild_pagewise.py` re-parses the saved page raws and applies the current merge
without model calls, so a merge change does not require re-running inference.
`audit_pagewise_rows.py` fails on a missing page, a non-`stop` page, an output
budget hit, or a context overflow. `scripts/reconcile_invoice_totals.sh` runs
rebuild + OCR + score + summarize + audit end to end.

### OCR total reconciliation (deterministic, no model)

The vision model sometimes drops leading digits on amounts with space thousands
separators: `R25 083.76` read as `2 508.36`, or `N$70 390.50` as `390.50`.
Printed totals are large, labelled, and arithmetic-checkable, so
`totals_ocr.py` reads the **final page** with tesseract (RapidOCR fallback) and
returns subtotal, tax, total, and the printed currency symbol/code.

A block is used only when all three labels are found **and**
`subtotal + tax == total` within tolerance **and** the implied tax rate is
0-35%. The parser handles space/comma thousands separators, European
`1.234,56` order, German `MwSt`, trailing ISO codes, and common OCR confusions
such as `RI75` for `R175`. When a consistent OCR block disagrees with the model,
the merge replaces the three printed amounts and records
`totals_from_ocr:...`; a printed symbol/code also overrides the model's currency
and records `currency_from_ocr_totals`. Line items, dates, and text fields are
never changed.

This is not gold and not a model call. It is an independent read of the same
printed totals. It can fail on damaged or low-resolution pages, in which case
the block is ignored and the model values stand. It is an evaluation/SDK
robustness path, not a benchmark-answer lookup.

**Measured on the 10 multipage documents:** all 10 final pages produced a
consistent OCR block, and applying it with the merge moved key-header from
86/90 (merge only) to **90/90**, and fully correct from 8/10 to **10/10**. The
line-item F1 is unchanged at 0.848 because OCR touches only the three printed
totals and currency. See the page-wise section for the full ladder and caveats.

### SDK product path

`InvoicePipeline` (`sdk/tinydoc/invoice.py`) is the productized version of this
probe. It owns the canonical page prompt, the product merge, the arithmetic
review flags, and the OCR total reader (`sdk/tinydoc/ocr_totals.py`). The
evaluation runner keeps a frozen copy of the merge so the measured run stays
reproducible, and a parity test replays every saved page-wise raw through both
merges. Changing the SDK merge therefore changes the product, and a rebuild that
changes the evaluation merge changes the measured result; the test fails if the
two drift. See `tests/test_invoice_sdk.py`.

### Degraded multipage probe (measured 2026-11-12)

`degrade_pages.py` renders a deterministic photo/scan copy of the same 46 pages
(downscale to 1100 px then upscale to 1400, rotation up to 1.2°, Gaussian blur,
brightness/contrast jitter, Gaussian noise, JPEG quality 58; seed 42) so the
pipeline can be tested beyond clean PDF text. The recipe is recorded in
`results/degrade_mp_recipe_42.json`. The clean-probe numbers are not evidence
about degraded uploads.

| Metric | Clean (10 docs) | Degraded (8 complete docs) |
|---|---:|---:|
| Documents completed | 10/10 | **8/10** |
| Key-header accuracy | 100% (90/90) | **98.6% (71/72)** |
| Fully correct | 10/10 | **7/8** (exact 95% CI 47.3–99.7%) |
| Mean line-item F1 | 0.848 | **0.795** |
| All line items right | 1/10 | **0/8** |
| OCR consistent blocks | 10/10 | **10/10** |
| p50 latency per document | 70.7 s | **101.1 s** |

Two documents failed on a page; the audit explicitly allows those two failures and lists them:

- `multipage-3p-gb-4` page 1: the model emitted malformed JSON (an arithmetic
  expression in the total field). A targeted retry reproduced the failure.
- `multipage-6p-za-8` page 5: Ollama returned HTTP 500 under memory pressure. A
  targeted retry hit another HTTP 500 on page 1.

The scorer therefore sees 8 documents, not 10. OCR totals were consistent on
**all 10 degraded final pages**; the parser corrected three amounts or currency
values. Paired against the clean run on the same 8 documents: key-header
72/72 → 71/72, fully correct 8/8 → 7/8, line F1 0.8525 → 0.795. This is a
robustness probe, not a production claim. Artifacts:
`results/summary_invoice_qwen3-vl_2b_mp_pagewise_degraded_ocr.json`,
`results/compare_invoice_clean_vs_degraded_2b.json`,
`results/audit_invoice_qwen3-vl_2b_mp_pagewise_degraded_ocr.json`,
`results/rows_invoice_qwen3-vl_2b_mp_pagewise_degraded_retry*.jsonl`.

The default page-wise audit is strict (`--allow-failed 0`). To reproduce this
probe, pass the two known failures explicitly:
`ALLOW_FAILED=2 scripts/reconcile_invoice_totals.sh <rows> <tag>`. The audit
still lists both failures and records `allowed_failures: 2`; it is not a silent
pass.

### Deterministic arithmetic review checks

`arithmetic_checks.py` flags a prediction when `subtotal + tax` disagrees with
`total`, or when the line items do not sum to `subtotal`. It uses a fixed
tolerance, never changes values, and never reads gold answers. It is a review
signal, not the benchmark's model-predicted `flag` field. On the existing
predictions it catches most arithmetic-inconsistent documents but also routes
documents whose extracted numbers do not reconcile; measure it on your own mix
before using it as a gate.

## Files

  `--all-pages`), emit JSONL with the benchmark's expected values and
  `image_paths`. Requires pypdfium2.
- `manifest_v1.jsonl` — local page-1 manifest (absolute image paths; not
  committed because the corpus lives on the external disk). Rebuild with the
  command below.
- `manifest_multipage.jsonl` — local all-pages manifest for the 10 multipage
  documents (46 pages, ≤1400 px; not committed for the same reason).
- `run_invoice_eval.py` — all-pages Ollama runner; writes per-document rows and
  a benchmark-format `predictions.json`. Records `prompt_eval_count`,
  `eval_count`, and `done_reason` so a context or output cut is visible.
- `run_invoice_pagewise.py` — one-page-per-request runner with deterministic merge
  and prompt v1/v2 support; v1 is canonical.
- `audit_multipage_rows.py` — fails on a missing page, a non-`stop` completion, a
  context overflow, or an unaccounted failure; `--allow-failed N` keeps visible
  failures in the denominator.
- `audit_pagewise_rows.py` — page-wise audit: every page present, parsed, `stop`,
  and within the context/output budget.
- `rebuild_pagewise.py` — rebuild predictions from saved page raws; optional
  `--ocr-totals` applies the final-page OCR reconciliation without model calls.
- `degrade_pages.py` — deterministic photo/scan degradation of a page manifest
  (downscale, rotation, blur, noise, JPEG); recipe seed is recorded.
- `compare_multipage.py` / `compare_pagewise.py` — paired comparisons with
  latency and exact sign tests.
- `summarize_scores.py` — compact summary; includes an exact Clopper-Pearson
  interval for the fully-correct rate.
- `totals_ocr.py` — thin wrapper over `sdk/tinydoc/ocr_totals.py`; the
  implementation is shared with the product path.
- `arithmetic_checks.py` — deterministic subtotal/tax/total and line-sum review
  flags; no model, no gold.
- `merge_multipage_runs.py` — splice a targeted retry into canonical rows.
- `build_pt_manifest.py` — download/verify the two Zenodo Portuguese archives,
  normalize the five scoreable fields, deduplicate repeat photos, and write the
  real-document manifests. See `PT_REAL.md`.
- `prepare_pt_probe.py` — apply the product's page cap (1400 px by default) and

- `pt_score.py` — five-field scorer for the Portuguese probe, using the same
  vendor/number/date/money rules as the benchmark scorer.
- `preds_from_pagewise_rows.py` — rebuild merged and raw prediction files from
  saved rows without dropping merge-sanity flags.
- `audit_pt_rows.py` — page/parse/completion/output-budget audit for the

- `analyze_pt_errors.py` — residual categories (dot-decimal misreads,

- `make_pt_holdout.py` — draw the disjoint seed-43 holdout from the 843

- `compare_pt_probes.py` — unpaired development-vs-holdout comparison with both

- `PT_REAL_RESULTS.md` — the measured development and held-out results,

```bash

git clone --depth 1 https://github.com/DrewKraken/invoice-extraction-benchmark \
  "/Volumes/KIOXIA 1TB/tinydoc/invoice-extraction-benchmark"
git clone --depth 1 https://huggingface.co/datasets/drew-ipp/invoice-extraction-benchmark \
  "/Volumes/KIOXIA 1TB/tinydoc/invoice_benchmark_v1"

# 2. Render page 1 and build the manifest (needs pypdfium2; a venv is cleanest)
#    python3 -m venv .venv && .venv/bin/pip install pypdfium2 pillow
python3 evaluation/invoice/build_manifest.py \
  --corpus "/Volumes/KIOXIA 1TB/tinydoc/invoice_benchmark_v1/corpus/v1" \
  --render-dir "/Volumes/KIOXIA 1TB/tinydoc/invoice_benchmark_v1/rendered" \
  --out evaluation/invoice/manifest_v1.jsonl

  --markdown scores.md --allow-missing

# 5. Degraded multipage probe (deterministic; recipe seed 42)
SCRATCH="${TMPDIR:-/tmp}/tinydoc_degraded"

  scripts/run_invoice_pagewise.sh qwen3-vl:2b-instruct \
  qwen3-vl_2b_mp_pagewise_degraded 1
```

## Normalization choices

The runner maps the model output into the benchmark schema and resolves date
ambiguity before scoring. The benchmark scorer parses dates day-first, which
would silently flip `03/12/2024` on a US invoice; the runner uses the document
id/currency (`-us-` or USD → month-first, otherwise day-first). Amounts accept
dot decimals, comma decimals, thousands separators, and parenthesized negatives.
Unparseable dates are passed through unchanged and scored as wrong.

`document_type` maps `credit`/`credit note` to `credit_note` and
`statement`/`other` to `other`; everything else defaults to `invoice`.

## Reporting rules

- Name it **“synthetic invoice transfer probe (Invoice Extraction Benchmark v1)”**.
- Never cite it as real-invoice accuracy or an external/independent benchmark.
- Always say **page 1 only**.
- Report key header field accuracy and fully-correct rate; line-item F1 and
  flags separately.
- Keep the per-category breakdown visible: clean digital PDFs and phone photos
  are different products.
